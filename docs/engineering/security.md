# Security architecture (WI-008)

CareerOS is a **single-owner** application: one allowlisted Google account, one database. This page describes the controls that exist and the limits that remain. It is not an audit or certification. For vulnerability reporting see [SECURITY.md](../../SECURITY.md). The decision is [ADR-012](../architecture/decisions.md#adr-012--single-owner-google-sign-in-server-sessions-and-web-push-wi-008).

## Threat model

Protected assets: the owner's schedule, study and job records (including recruiter contacts, compensation notes and reflections), Google refresh tokens, push subscriptions and all server secrets. Considered adversaries: anyone on the internet who can reach the app URL, a different Google account holder, a malicious page in another tab (CSRF, clickjacking, open redirect), a network observer, and accidental leaks through logs, exports or backups. Out of scope: a compromised owner device or Google account, a compromised host or database provider, and multi-user tenancy (US-026).

## Sign-in

Google OpenID Connect, Authorization Code flow with PKCE (S256), `state` and `nonce`, scopes `openid email` only (`src/features/auth/`). Calendar access is a separate consent (ADR-010); signing in never grants it.

1. **Sign in with Google** is a Server Action (same-origin check by Next.js). It stores `{state, verifier, nonce, next, exp}` in an AES-256-GCM encrypted, httpOnly, SameSite=Lax cookie scoped to `/api/auth`, valid 10 minutes, and redirects with `prompt=select_account`.
2. `/api/auth/callback` requires that cookie, compares `state` in constant time, checks expiry, deletes the cookie (one use), and exchanges the code server-to-server with the client secret and PKCE verifier.
3. The ID token arrives directly from Google's token endpoint over TLS, so its claims are validated without a JWKS signature check (OIDC Core §3.1.3.7): issuer is Google, audience is our client ID, not expired, `iat` not in the future, nonce matches, `email_verified` is true, and the email equals `OWNER_EMAIL`. The access token is discarded.
4. Any failure redirects to `/login?error=<code>` with a generic message. A different account sees "This CareerOS workspace is private"; nothing is created for it.
5. `next` is only ever a same-origin path (`safeNext` rejects `//host`, `/\host`, schemes and `/login`), so there is no open redirect.

## Sessions

Server-side `Session` rows (`src/server/session.ts`). The browser holds a random 256-bit token in `careeros_session` (httpOnly, SameSite=Lax, `Secure` whenever `APP_BASE_URL` is HTTPS, path `/`, 30 days). Only its SHA-256 is stored, so a database leak does not yield usable cookies. Every request checks: well-formed token, row exists, not revoked, not expired, and the user's email still equals `OWNER_EMAIL`. `lastSeenAt` is updated at most hourly. **Sign out** revokes the row server-side, so a copied cookie stops working immediately (verified in all three browser engines). Changing `OWNER_EMAIL` locks out every existing session. There is no idle timeout shorter than 30 days, no device list and no MFA beyond what the Google account enforces.

## Access control

`src/proxy.ts` runs before every route except static build assets:

| Path                                                                                                         | Rule                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/notifications/process`, `/api/calendar/sync`                                                           | `Authorization: Bearer $CRON_SECRET` (constant-time), otherwise 401. A session cookie is not accepted.                                                                    |
| `/login`, `/privacy`, `/api/auth/callback`, `/api/health`, `/api/calendar/webhook`, manifest, `sw.js`, icons | Public. The privacy page is static text with one contact address; health returns status words only; the webhook validates channel ID, resource ID, token hash and expiry. |
| Every other page                                                                                             | Valid session, else redirect to `/login?next=<path>`. No navigation or data is rendered while signed out.                                                                 |
| Every other `/api/*` route                                                                                   | Valid session, else `401 {"error":"unauthorized"}`.                                                                                                                       |

The proxy is the first gate, not the only one: pages and Server Actions call `owner()`, which re-resolves the session and redirects if it is gone, and every service scopes queries and writes to that owner. Server Actions keep Next.js' Origin check (CSRF); cookies are SameSite=Lax; there are no state-changing GET routes (export is read-only).

## HTTP hardening

- **CSP** per request with a fresh nonce: `script-src 'self' 'nonce-…' 'strict-dynamic'` (no `unsafe-inline`/`unsafe-eval` in production), `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`, `form-action 'self'` plus Google's sign-in origin, `connect-src`/`img-src`/`worker-src`/`manifest-src 'self'`. `style-src` allows inline styles (React style attributes); no user content is rendered as HTML. `upgrade-insecure-requests` is sent only when `APP_BASE_URL` is HTTPS.
- **Static headers** (`next.config.ts`): `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cross-Origin-Opener-Policy: same-origin`, a restrictive `Permissions-Policy`, and `Strict-Transport-Security: max-age=31536000; includeSubDomains` in production. `X-Powered-By` is removed.
- **Caching:** private pages and APIs send `Cache-Control: private, no-store`. The service worker caches nothing.
- **Rate limits** (in-process, per client IP per minute): sign-in action 20, `/api/auth/callback` 30, `/login` 60, calendar webhook 300; excess gets 429. The IP is the first `X-Forwarded-For` entry, so the limit is only as trustworthy as the proxy in front of the app. It is defense in depth for public endpoints, not an authentication control, and a multi-instance deployment gets a per-instance limit.

## Secrets and logging

Secrets are environment-only and validated at start-up without printing values ([environment reference](environment.md)). Logs use a fixed vocabulary: `[auth] signed-in`, `[auth] sign-in rejected <code>`, `[notifications] processed {counts}`, `[calendar] … {userId, counts, codes}`, `[study] grill made {model, provider, tokens, ms}`, `[study] grill failed <ErrorClass>` (an answer that broke the format adds rule codes such as `rungs.2.points:too_small`: positions and rules, never text), `[study] provider check failed <ErrorClass>`, `[agent] chat made {model, provider, tools, micros}` (a count of tools, never their names, arguments or results), `[agent] chat failed <ErrorClass|ProviderMismatch|NoAnswer>`, `[prep] doc made {searches, sources, official, ms}`, `[prep] doc failed {searches, sources}|<ErrorClass>`, `[deletes] failed <ErrorClass> <code>` (a Prisma or driver code such as `P2039`, never the record), and failures as a fixed message plus the error class name (`Notification processing failed TypeError`). They never contain tokens, codes, cookies, keys, push endpoints or keys, email bodies, notes, reflections or contacts. `JobRun.lastError` stores only the error class name. A scan of 479 production-server log lines from the WI-008 browser runs found no secret values or token patterns.

## Data leaving the server

- **Google:** during sign-in, only the OAuth exchange. Calendar: see ADR-010 (titles, instants, category, private IDs).
- **Push services** (Google FCM, Mozilla, Apple): an encrypted payload (RFC 8291, aes128gcm) with a title, one general line for the reminder's type, a tag and a same-origin path, plus a VAPID JWT (RFC 8292). Push services cannot read the payload. Since R2 the line is fixed per type, so a lock screen never shows a block title, company, round, note or item name (`tests/push-privacy.test.ts` checks every type).
- **Presence (WI-028):** `POST /api/presence` is a private API behind the session like every other. It stores one timestamp, `User.lastActiveAt`, at most every two minutes, and nothing about the page. Study Nudges use it only to keep a reminder inside the app while Silsila is open.
- **Command bar (WI-036):** `GET /api/command` (today's commands) and `POST /api/command` (search) are private APIs behind the session and scoped to the owner. The search words travel in the POST body, never in a URL, because they may become a note to self. Neither is cached or logged, and nothing is written except the note the owner explicitly adds.
- **Grill Me (WI-031, ADR-022):** only when the owner presses Send, the roadmap item's ticked fields (title, scope, "done when", reference names without links, each length-limited by `studyInput`) go to OpenRouter over HTTPS with the server-only `OPENROUTER_API_KEY`, pinned to `anthropic/claude-haiku-5.5` on `google-vertex/global` (zero data retention, `only` the one endpoint, `allow_fallbacks: false`, `data_collection: "deny"`). Notes, "asked at", links, the schedule, sessions, jobs and reflections are never read into a payload (`tests/ai-domain.test.ts`). An answer reported from any other provider blocks AI until the owner checks again. The public endpoint and ZDR lists are read without the key. No prompt or answer is stored; the ledger (`AiUsage`) holds model, endpoint, tokens, cost and time. The browser never talks to OpenRouter; the CSP is unchanged.
- **Listen (WI-037, ADR-023):** the only outbound fetch of third-party pages. It happens only when the owner presses Fetch sources and write, and only for the item's own reference links over HTTPS on the two site lists in `src/features/listen/domain.ts`. Redirects are followed by hand and only to listed sites (at most three). Requests have an 8-second timeout, read at most 1.5 MB, and accept HTML or plain text. The request carries a fixed `User-Agent` and no cookies or credentials. The model receives the item's title, scope and done-when plus the picked passages, never notes or "asked at" (`tests/listen-database.test.ts`). Nothing is stored. Logs are `[listen] sources {fetched, failed, passages}` and `[listen] checked {kept, unsupported, one-source, code}`: counts only, never URLs or text.
- **Ask Rumi (WI-040, ADR-024):** only when the owner sends a message, the pinned zero-retention endpoint receives the question, the last 12 messages of that conversation, the owner's "Rumi knows" lines and the system prompt, then the results of the read-only tools the model calls (`src/features/agent/tools.ts`). Each tool selects only the fields it sends, so notes, check-in notes, interview reflections (`topicsAsked`, `wentWell`, `toImprove`, `outcomeNotes`), interviewers, meeting links, locations, compensation, recruiter and hiring contacts, job descriptions, next-action text, block descriptions and skip reasons are never loaded. Blocks outside the owner's study categories and job search go as "busy hh:mm–hh:mm"; roadmaps with Study AI off and test-named records are left out (`tests/agent-database.test.ts` plants a marker in every one of those fields and checks every tool's output and every request). Tool arguments are validated and refused when unknown; tool results are data in the prompt, never instructions. Rumi has no write tool: since WI-041 `propose_blocks` and `suggest_memory` only make cards stored with the answer. Add to plan (`applyProposal`) and Keep (`answerSuggestion`) are the owner's own server actions; they load the answer by id and owner, re-check every block against the day under the owner lock (after generating that day's routines), write through `saveBlockIn` all or none, and offer Undo (`cancel-blocks`). Proposals are limited to today through Sunday, six blocks each and two per answer; a conflict names another block only by time and, outside study and job search, as "busy". Conversations and lines are owner records (deletable, exported); tool results are not stored, and the ledger row of each call holds cost and tokens only. The owner's messages are limited to 30 an hour and 100 a day, a message to 6 model calls, and the US$3 monthly stop is shared with Grill Me and Listen. Since WI-055 the page asks through `POST /api/rumi/ask`, which streams newline-delimited JSON: each read's tool name as it starts, then the stored answer. It refuses a request whose `Origin` host differs from its `Host` (403); the session cookie is `SameSite=Lax` as well. The question travels only in the body, and no answer text leaves before it is checked and stored.
- **Prep docs (WI-042, ADR-024):** only when the owner presses Research and write on an application. `searchQueries` builds at most six searches from the company, the role, the upcoming round types and the formats ticked on the application (WI-047, fixed words such as "code review interview"); each is the whole user message of a request with the `web` plugin (`engine: "exa"`, three results) on the pinned zero-retention endpoint, so Exa, a third party without a zero-retention promise, sees only those words (`tests/prep-database.test.ts` plants markers in notes, compensation, contacts, round titles and the job description and checks every search). The writing call (`PREP_FORMAT`, 3,000 tokens) gets the search notes, the cited sources, the rounds (title, type, date and, when stated, whether AI is allowed), the ticked formats, roadmap item titles from Study AI roadmaps and problem titles; the job description only when ticked. Web text is data in the prompt; `readPrepDoc` keeps only points that cite a real source id and links that name the owner's own items. Sources are HTTPS links, marked Official only on the company's own domain or the posting's host. Five docs a day; each call is a `PREP_RESEARCH` ledger row inside the US$3 month. Logs are `[prep] doc made {searches, sources, official, ms}` and `[prep] doc failed …` with counts or the error class only.
- **Export** (`/api/export`, signed-in only): a JSON copy of domain records. It excludes the refresh token, sync token, channel tokens, session hashes, push endpoints and keys, and maintenance records.

## Dependencies

`pnpm audit` reports no known vulnerabilities (2026-10-27, WI-044), in production and development dependencies alike. The UAT audit of that day found Next.js 16.3.6 exposed to two critical advisories (GHSA-2464-fhr4-w9xw and GHSA-673q-mjm6-r5xr, unauthenticated remote code execution in Image Optimization and `use cache`; `/_next/image` is outside the auth proxy) and several high ones. The fix:

- Next.js and `eslint-config-next` 16.4.3, zod 4.6.7, Prisma 7.10.1, vitest 5.0.5;
- `pnpm-workspace.yaml` overrides for transitive packages without a patched parent (`source-map-js` ≥ 1.2.2, `fast-uri` ≥ 3.1.9, `vite` ≥ 8.3.3).

CI now runs `pnpm audit --prod --audit-level high` after installing, so a high or critical advisory in a production dependency fails the build, and Dependabot (`.github/dependabot.yml`) opens weekly update pull requests for the owner to review.

## Known limits

Single owner only (no tenant isolation or roles). The rate limiter is per process. No audit log of sign-ins beyond the `Session` rows. The health endpoint is public by design (status words only). No automated secret rotation. Backups are as safe as the storage the operator chooses.
