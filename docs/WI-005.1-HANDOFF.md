# WI-005.1 — Database time integrity and schema drift handoff

Narrow pre-calendar hardening. No product features, UI changes or Google Calendar work.

## Root cause (confirmed in `@prisma/adapter-pg` 7.10.0)

- **Write:** `formatDateTime` sends a `Date` as its UTC wall clock without an offset (`2026-07-15 14:00:00`). PostgreSQL converts that literal to `timestamptz` using the **session** `TimeZone`.
- **Read:** `normalize_timestamptz` replaces the offset PostgreSQL returns with `+00:00`.

In a non-UTC session both steps shift by the same offset, so the app looked correct while the stored instant was wrong. On a Toronto server, `2026-07-15T14:00Z` was stored as `18:00Z` (EDT) and `2026-01-15T14:00Z` as `19:00Z` (EST). Prisma fills `@default(now())` and `@updatedAt` on the client, so **every** app-written `timestamptz` column was affected. `DATE` values are formatted from UTC date parts and were never affected.

## UTC session solution

`src/lib/database.ts` → `utcConnectionString()` merges `-c TimeZone=UTC` into the connection string's startup `options`. Existing options such as `search_path` are kept, and a TimeZone set earlier in the URL is overridden. `createPgAdapter()` wraps it. Every connection uses it: `src/server/db.ts`, `prisma.config.ts` (migrations), seed, verify-seed, the timestamp scripts and all database tests.

`src/instrumentation.ts` checks `SHOW TimeZone` for the **app session** when the server starts:

- A non-UTC session stops the server.
- A non-UTC **server default** without a recorded repair only logs `pnpm timestamps:audit` guidance.
- Connection errors only warn.

## Audit and repair

- **`pnpm timestamps:audit`** is read-only. It reports:
  - the server default zone, the app session zone and the ledger state
  - per-table and per-column non-null counts
  - DST-ambiguous rows
  - future-`createdAt` evidence of a shift
  - samples (table, ID, column, stored value, value if repaired), with no credentials or personal text
  - the `DATE` columns that are left alone
  - an honest assessment noting that a value alone cannot prove a shift
- **`pnpm timestamps:repair`** is a dry run by default: the full repair inside a transaction, then a rollback. `--apply --confirm=<current database>` commits.
- **Guards:** a valid IANA zone (UTC aliases refused), the zone must equal the server default unless `--force-zone`, confirmation required, the app session must be UTC, a transaction-scoped advisory lock, a ledger check, one `UPDATE` per table (so cross-column CHECKs see consistent values), a comparison of non-null counts before and after, and start/end ordering checks for ActualSession, TimeBlock and InterviewRound. Any failure rolls back.
- **Formula:** `T = (S AT TIME ZONE L) AT TIME ZONE 'UTC'`, applied per row with that date's IANA offset.
- **DST proof:** tests recover `2026-01-15T14:00Z` (stored as 19:00Z, EST) and `2026-07-15T14:00Z` (stored as 18:00Z, EDT) exactly, and `2026-11-01T01:30Z` (a wall clock in the repeated hour) exactly. `2026-03-08T02:30Z` (a wall clock in the skipped hour) becomes 03:30Z and is counted as ambiguous, because it is indistinguishable from a genuine 03:30.
- **Double-repair protection:** a `MaintenanceRecord` row with id `timestamp-repair:legacy-session-zone:v1` is written in the repair transaction. Later runs are refused under the advisory lock (`--allow-repeat` is a developer override). The startup check and the audit both report the ledger.

## RoutineBlock.weekdays drift

WI-002 added `weekdays INTEGER[] NOT NULL DEFAULT '{}'` only to backfill existing rows, then added `CHECK (cardinality 1..7)`. The default can never produce a valid row, and every writer supplies weekdays. Resolution: a new migration drops the default. `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` now exits 0.

## Migrations and schema

- `20260925090000_routine_weekdays_no_default`: `ALTER COLUMN "weekdays" DROP DEFAULT`.
- `20260925090100_maintenance_record`: `CREATE TABLE IF NOT EXISTS "MaintenanceRecord"`, plus the Prisma model.
- No shipped migration changed. All instant→date conversions (WI-003, WI-005) use explicit `AT TIME ZONE u.timezone` and don't depend on the session zone. They need correct stored instants, hence repair **before** deploying them on a legacy database.

## Test matrix

- UTC / America/Toronto / Asia/Tokyo server defaults: the pinned session reports UTC and stores the same instants (checked by an independent unpinned reader). An unpinned control reproduces the shift.
- URL merging: the pin is added, `search_path`/`sslmode` are kept, and a URL-supplied TimeZone is overridden.
- Legacy fixture (old unpinned writer on a Toronto server), end to end: audit, dry run (snapshot unchanged, no ledger), missing confirmation and wrong zone refused, apply, exact instants, 90-minute durations kept, `DATE` columns unchanged, the pinned app reads and formats Toronto times, the startup check is quiet, a second repair is refused.
- A UTC database is never repaired: audit reports none needed, and both the Toronto zone and a UTC legacy zone are refused.
- Ordering: a SQL-written row across the fall-back hour makes the repair fail, first through the `session_order` CHECK and then, with that constraint removed, through the tool's own check. Data and ledger are unchanged each time.
- `RoutineBlock.weekdays` has no column default.

## Known limitations

- Spring-forward-gap wall clocks can't be disambiguated (±1 h); they are counted.
- Rows that SQL itself wrote on a legacy database (the WI-002 `DailyPlan.generatedAt` backfill and imported-row `updatedAt`) were never shifted and are moved by the repair. Those are null-checks or metadata only.
- If the new app writes to a legacy database **before** the repair, the database holds a mix that no tool can separate. Stop the app, repair, then start. The startup warning is a reminder, not a block (per scope).
- A database created after WI-005.1 on a non-UTC server still gets the startup reminder until its default is set to UTC (`ALTER DATABASE … SET TimeZone='UTC'`), which is safe once there is no unaudited legacy data.
- Poolers that drop startup options need `ALTER DATABASE … SET TimeZone='UTC'`; the startup check catches it.

## Personal database procedure (do not automate)

1. Stop CareerOS. `pg_dump --format=custom --file=careeros-pre-wi0051.dump <personal db>`, then restore it into a scratch database to prove the backup works.
2. `psql <personal db> -c 'SHOW TimeZone'`. If it is UTC and always was, there is nothing to repair; skip to step 6.
3. Check out this branch (or merged `main`). `DATABASE_URL=<personal> pnpm timestamps:audit`. Save the output.
4. `DATABASE_URL=<personal> LEGACY_TIMESTAMP_TIMEZONE=<zone from step 2> pnpm timestamps:repair`. Review the dry-run counts and integrity output.
5. `DATABASE_URL=<personal> pnpm timestamps:repair --legacy-zone=<zone> --apply --confirm=<database name>`.
6. `DATABASE_URL=<personal> pnpm db:deploy` (WI-005 plus WI-005.1 migrations).
7. `pnpm timestamps:audit` should show the ledger. Start the app and check that routine/Today times, DSA attempt times and job dates look right, and that the server log has no time warning.
8. Optional: `ALTER DATABASE <personal> SET TimeZone = 'UTC'` to silence the startup reminder (only after the audit/repair).
9. Continue normal use. If something looks wrong, stop and restore the step-1 dump into a new database; never re-run the repair.
