# WI-017 handoff — UAT quick wins

Branch `feat/wi-017-uat-quick-wins` from `main` (after PR #22). Scope: the ten quick wins from the production acceptance pass of 2026-10-22 (the UAT report lives outside the repository with the owner's other review material). No schema change, no migration, no new dependency.

## 1. Outcome

1. **Done keeps the panel open in long sections.** The roadmap list was remounted when the section's default filter flipped from "Everything" to "Not done" after the first Done, which closed the row and hid "Next". The list key no longer includes the filter (`src/app/roadmap/[id]/page.tsx`), so the row stays open with its confirmation and the "Next: …" link while the filter still changes.
2. **Forms close after success and confirm with Undo.** `ActionForm` gains `closeOnSuccess` (closes the enclosing `Disclosure` through a new `useDisclosure` context) and `onSuccess`. Add block, Add interview and Add priority close on success; their results go to a `FeedbackOutlet` above the list (`blocks` on Today's timeline, `rounds` under Interviews, `priorities` on the review). A newly added block answers "Added for this day. Undo" (new undo kind `cancel-block`); a saved priority answers with Undo (`remove-priority`). `saveBlock` reports whether it created or changed the block so the message can say so.
3. **Inline required-field messages.** `ActionForm` captures the browser's `invalid` event, prevents the native bubble, marks the first refused field (`.is-invalid`), focuses it and prints one sentence under the form: "Title is required.", "Answer “How did it go?” first." (from the fieldset legend), "… does not look right." or "… is out of range." for other constraints.
4. **Top progress bar.** `src/components/progress-bar-top.tsx` keeps a tiny module store (`startProgress` / `stopProgress`) and renders a 2 px teal bar fixed to the top of the viewport. It starts on any internal link click, on every `PendingRegion` transition (section and filter changes, Save and continue) and while an `ActionForm` is pending; it clears when the URL changes, when the action settles, or after a 10 s guard. Mounted once in the root layout.
5. **Greeting line and chain caption.** Today's heading is followed by "Good morning · N blocks planned · N revisions due" (greeting from the owner's local hour; revisions only for today). The chain carries "N of the last 14 days with recorded work" so the rings explain themselves.
6. **Attempt form resets fully.** After "Attempt saved. Next revision …" the How-did-it-go choice, the inferred confidence and the touched state are cleared through `onSuccess`, so the next attempt starts from nothing chosen.
7. **Review heading and push status.** The weekly review heading uses the body sans like every other page. Settings → Notifications reads one sentence: "This device: enabled/not enabled · N devices enabled in total; reminders always stay on Today." (device count passed to `PushControls`).
8. **Stage stepper.** The application page shows the pipeline as a pill group under the heading (Saved → … → Offer, done stages in teal, the current stage filled and disabled, Rejected and Withdrawn as quiet closed stages at the end). Each pill is a submit button of one `ActionForm` around `stageAction`, so a click moves the stage with the same history record and Undo as before. The "Change stage" disclosure and its select are gone.
9. **Phone timeline.** Under 700 px each block leads with Start only; Complete, Skip and Cancel block (and the skip reason) sit behind a "More actions for …" ellipsis toggle (`src/features/execution/secondary-actions.tsx`). On wider screens the toggle is hidden and the actions render inline as before.
10. **Success messages with a link stay 8 s.** Already in place since WI-016 (`ActionState.link`); nothing to change.

## 4. Notes

- Dev database side effects of the checks: one attempt on Two Sum, the first Backtracking item was marked Done and then reopened (now In progress), a block "WI-017 check" was added and cancelled through Undo. Nothing in production.
- The inline invalid message depends on the browser firing `invalid` on submit; forms without `required` attributes are unaffected.
- On very slow hydration (a background tab on the dev server) the first click on the phone More toggle can land before React attaches; the toggle is a plain button and works from the next click. Production hydrates well under a second.
