# WI-008.2 handoff — Render + Supabase free-tier deployment path

Branch `feat/wi-008-2-render-supabase` on `main` at `20ef306` (PR #9, WI-008.1). Prepared 2026-10-02. Documentation and one blueprint file; **no application code changed**, so the WI-008.1 verification (218 tests, build, Docker rehearsal) still describes the deployed image.

## 1. Outcome

The GitHub Student Developer Pack credit that would have funded Heroku was still not granted six days after application. Rather than pay before the product has proven its daily value, hosting moves to **Render's free web service** (Docker runtime, built from the unchanged `Dockerfile`) and **Supabase's free PostgreSQL 17** (reached through the IPv4 session pooler). Cost is $0 with no card. Heroku stays documented as the alternative and `heroku.yml` remains, so the ADR-013 exit path works in both directions. Recorded in [ADR-014](architecture/decisions.md#adr-014--render-and-supabase-free-tiers-while-the-heroku-credit-is-pending).

## 3. Facts verified on 2026-10-02

- Render free: 750 instance hours per workspace per month; spin-down after 15 idle minutes with about a one-minute wake; custom domains and managed TLS included; **no shell and no one-off jobs**; Docker runtime supported; `PORT` injected (default 10000) and the service must bind `0.0.0.0`, which `next start` does.
- Render has no outbound IPv6. Supabase's direct host is IPv6-only on the free plan; the session pooler (`aws-<n>-<region>.pooler.supabase.com:5432`, user `postgres.<ref>`) is IPv4 and supports prepared statements. The transaction pooler (6543) does not and must not be used with Prisma.
- Supabase requires TLS; the CA is downloadable from Project settings → Database → SSL. Free plan: PostgreSQL 17, 500 MB, Canada (Central) available, project paused after 7 idle days (the cron prevents this), session-pooler clients capped at the pool size (default 15; the app uses 5).
- Namecheap records per Render's guide: `A @ 216.24.57.1`, `CNAME www silsila.onrender.com`.
- Local: `pg_dump` from Homebrew `postgresql@16` is 16.14 and cannot dump a 17 server; `brew install libpq` provides a newer `pg_dump` at `/opt/homebrew/opt/libpq/bin`.

## 6. Known limitations

- The `PORT=10000` binding check passed after Docker Desktop was approved: `/login` answered 200 on port 10000 and the log showed Next bound there.
- Whether Supabase's session pooler forwards the `options=-c TimeZone=UTC` startup parameter is unverified until the project exists; the database default is UTC, and `/api/health` reports the session zone either way.
- `verify-full` against Supabase's CA is untested; `no-verify` is the starting mode.
- A fractional CPU: expect slower server renders than locally. Spin-down still happens if cron-job.org is down.

## 7. Go-live findings (2026-10-20)

- Supabase's Free plan allows two active projects **per account**, not per organisation; the owner's existing account was full, so Silsila's project lives in a second Supabase account created for it. Project ref `nyolnlvigrmrkmhdyndu`, Canada (Central), session pooler host `aws-1-ca-central-1.pooler.supabase.com`. Migrations were applied from the workstation; `SHOW TimeZone` reports `UTC`.
- Google Auth Platform: project `silsila-512219`, app `Silsila`, scopes `openid`, `userinfo.email`, `calendar.app.created` (all listed as non-sensitive), Calendar API enabled, web client `Silsila web` with the two `usesilsila.me` redirect URIs. Publishing to production requires a privacy policy URL, so the app stays in **Testing** with the owner as test user until a `/privacy` page exists. Consequence: Calendar's Google refresh token expires every 7 days until then; sign-in is unaffected.
- First Render deploy failed at start-up with `EACCES … pnpm install --production`: pnpm 11 defaults `verifyDepsBeforeRun` to `install`, judged the production `node_modules` stale once Render re-layered the image, and tried to install as the unprivileged user. Fixed by starting Next directly in the Dockerfile `CMD` and setting `verifyDepsBeforeRun: false` in `pnpm-workspace.yaml` (fix branch `fix/render-runtime-start`). The local rehearsal had not caught it because the image ran unchanged there, and forcing the check back on locally (touched lockfile, `npm_config_verify_deps_before_run=install`) still did not reproduce it, so the trigger is specific to Render's re-layered filesystem. The fix therefore removes pnpm from the container start path entirely rather than relying on the setting alone; the rebuilt image passed the rehearsal (health `ok/UTC/current`, redirects, cron gate) and starts cleanly on `PORT=10000`.
