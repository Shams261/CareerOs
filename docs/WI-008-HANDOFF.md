# WI-008 handoff — Personal production launch and hardening

Branch `feat/wi-008-production-launch`, rebased onto `origin/main` at `24d66f4` after WI-007 PR #6 was merged on 2026-09-25. Verified 2026-09-24 on disposable local databases with a loopback fake Google. **The owner's personal database and real Google account were not touched.**

## 1. Outcome

CareerOS can be deployed on the internet for one owner. Google sign-in and revocable server sessions replace Basic Auth. Reminders reach a closed app through Web Push, the app installs as a PWA, and the operator has health checks, job status, backups with restore verification, an export, and guides for each step. Out of scope and not started: new product modules, Redis, WI-009.

## 2. Authentication

Google OIDC (code + PKCE, `state`, `nonce`, `openid email`, account chooser), allowlisted by `OWNER_EMAIL` (verified email only). The sign-in state is kept in an AES-256-GCM cookie (`AUTH_SECRET`, 10 minutes, path `/api/auth`). ID token claims are validated per OIDC Core §3.1.3.7. A different account gets "This CareerOS workspace is private". A database that already has an owner never gets a second, empty one (`owner_mismatch`). `/login?next=` accepts same-origin paths only. Code: `src/features/auth/`, `src/app/api/auth/callback`, `src/app/login`.

## 3. Sessions and sign-out

`Session` rows store the SHA-256 of a 256-bit token. The cookie `careeros_session` is httpOnly, SameSite=Lax, Secure over HTTPS and lasts 30 days. The allowlist is re-checked on every request, and `lastSeenAt` is updated at most hourly. Sign-out revokes the row; the old cookie was verified to fail in all three engines.

## 4. Access control

`src/proxy.ts`: anonymous pages redirect to `/login?next=`, anonymous APIs get `401 {"error":"unauthorized"}`, and the cron endpoints are bearer-only. The public paths are login, the callback, health, the calendar webhook, the manifest, `sw.js` and icons. Pages and actions still resolve the owner (`owner()`) and scope every query.

## 5. HTTP security

Every request gets a fresh CSP nonce (`strict-dynamic`, `frame-ancestors 'none'`, `object-src 'none'`, restricted `form-action`), plus nosniff, `X-Frame-Options: DENY`, referrer policy, COOP and a permissions policy. HSTS is sent in production; `X-Powered-By` is removed; private responses are `no-store`. Rate limits per IP per minute: sign-in 20, callback 30, login 60, webhook 300. WebKit showed that `upgrade-insecure-requests` breaks plain-HTTP localhost, so it is sent only when `APP_BASE_URL` is HTTPS.

## 6. Environment validation

`src/lib/env.ts` groups the variables as core, auth, calendar (optional) and push (optional); Google endpoint overrides must be loopback URLs. In production, invalid configuration **exits with code 1** and prints `NAME: reason` lines, never values (verified). `APP_PASSWORD` was removed everywhere, including CI. See the [environment reference](engineering/environment.md).

## 7. Database

`DATABASE_POOL_MAX` sets the pool size (default 5, idle timeout 30 s). The UTC session pin and start-up check from WI-005.1 are unchanged. The deployment guide covers transaction poolers (`ALTER DATABASE … SET TimeZone = 'UTC'`).

## 8. Migration `20260928090000_production_launch`

It adds `Session`, `PushSubscription`, `JobRun` and `NotificationLog.pushAttempts`, with CHECK constraints (non-negative counters, session expiry after creation). Existing reminders get `pushAttempts = 3`, so no backlog is pushed. It is additive only. The WI-007 → WI-008 upgrade is tested; drift is zero.

## 9. Web Push

The same cron request that creates inbox rows pushes them with VAPID and an aes128gcm payload (TTL 12 h). Each row gets at most 3 attempts, only within 2 h of being due. 404/410 revokes a device immediately, and 5 consecutive failures revoke it. The inbox is always kept. Devices opt in explicitly in Settings, where they can also send a test or disable the device. Push APIs are not called before opt-in; this also fixed a reload loop in Playwright's WebKit. The daily progress reminder reaches a closed app (tested). See [notifications and PWA](engineering/notifications-pwa.md).

## 10. PWA

The manifest is standalone, starts at `/today` and uses theme `#244e3b`, with 192/512/maskable icons and an Apple touch icon (generated by `scripts/generate-icons.mjs`, no dependencies). The service worker handles push and click only, caches nothing and opens same-origin paths only. There is no offline mode.

## 11. Honest mobile limits

Settings and the guide state the limits. iPhone/iPad need iOS 16.4+ and the Home Screen app. Desktop browsers must be running. Focus and battery modes can delay alerts. **Real-device delivery has not been verified**, because automated browsers cannot hold push subscriptions.

## 12. Health, job runs, Settings

`GET /api/health` is public and returns `{status, database, sessionTimeZone, schema}` only (200 or 503). `JobRun` records each cron run's start, success or failure, error class and counts. Settings now has Account, Getting started, Notifications, System status and Your data.

## 13. Export

`/api/export` (signed-in only) returns a JSON attachment of domain records. It excludes refresh/sync/channel tokens, session hashes, push endpoints and keys, and maintenance records (tested).

## 14. Backups

`pnpm db:backup` writes a custom-format dump (mode 600, SHA-256, credentials passed via environment). `pnpm db:restore:verify <file>` restores into a **new** scratch database only, refuses existing names, checks migrations, counts and data age, then drops it. Both were verified locally. See [backup and restore](engineering/backup-restore.md).

## 15. Logging

The vocabulary is fixed: `[auth] signed-in`, `[auth] sign-in rejected <code>`, `[notifications] processed {counts}`, `[calendar] … {ids, counts}`, and error class names. A scan of 479 production-server log lines found no secret values and no token or personal-text patterns.

## 16. Accessibility

axe-core with WCAG 2.0/2.1/2.2 A and AA rules was run on 12 pages (login, 7 main pages, 4 detail pages) at 1440 and 390 px. It found 555 contrast failures and 4 target-size failures; all are fixed and **24 of 24 audits are now clean**. Fixes: a defined `--muted` token (#5c6b60, ≥ 5:1), darker yellow pill text, 24 px checklist spacing, and a focus ring on select, textarea and summary. A manual screen-reader pass is still recommended.

## 23. Personal database migration (owner-run)

Follow [backup and restore → Migrating an existing personal database](engineering/backup-restore.md#migrating-an-existing-personal-database):

1. Stop the app and the scheduler.
2. Run `pnpm db:backup`, then `pnpm db:restore:verify`.
3. Run `SHOW TimeZone`, then `pnpm timestamps:audit`.
4. Only if needed: a repair dry run, then apply.
5. Run `pnpm db:deploy`.
6. Check that the stored `User.email` equals your Google email.
7. Update the environment (remove `APP_PASSWORD`, add the auth, Google and VAPID variables).
8. Start the app and verify: health, sign-in, local times, Settings status.

## 24. Real Google and onboarding checklists (owner-run)

- [Google production checklist](engineering/google-production.md): a web client with both redirect URIs, `openid email` plus `calendar.app.created`. Use publishing status _In production_ if you use Calendar, because _Testing_ expires refresh tokens after about 7 days. Then verify owner sign-in, refusal of another account, and Calendar connect.
- [Onboarding checklist](product/onboarding.md): profile and timezone, routines, DSA and learning focus, applications, per-device notifications with a test, a closed-app reminder check on each phone and laptop, Calendar, Prepare next week, and an export.

## 25. Known limitations, suggested commits, next steps

**Limitations:**

- Push is not verified on real devices.
- iOS push requires the Home Screen app.
- Rate limits are per process and trust the first `X-Forwarded-For` entry.
- Single owner only; recovering from a lost Google account means editing the database.
- No offline mode; no in-app data erasure.
- Local performance numbers only.
- The Prisma CLI tooling advisories remain (US-027).
